Schema Before Data

A meeting about building a knowledge graph opens with talk of data, but the first thing that lands in the repository is not data — it is a dictionary. What shall we call a class, what counts as a relation, which key decides that two records are the same thing. Settled before a single row is loaded, these decisions look like bureaucracy whose only product is longer meetings. Putting a national address knowledge graph on top of a national standard ontology taught me the opposite. Fixing the schema first is a payment, and there is something definite you get for it.

DP
Daeseung Park AI & Software Systems Engineer · KAIST September 2026 · 17 min read
1-min summary An ontology is not a fancier word for database design. It is fixing the concepts before the instances arrive, and that act decides what you will and will not be able to do later. This piece sets out the four things I got in return for putting a national address knowledge graph on top of a standard ontology. ① Documents cannot drift from the implementation — with a single class dictionary as the source of truth, and the spec, the RDF/OWL file, the JSON-LD context, the SHACL shapes, the data dictionary and the database constraints all generated from it, the path along which they could diverge simply does not exist. ② You get to choose what stays open and what gets locked — what should remain open-world (whether a relation exists at all, how much it is trusted) and what should be closed-world (required properties, identifier uniqueness) are assigned to different tools on purpose. ③ Identifiers exist before the model does — declare a business key alongside each class and that one line becomes the basis for idempotent loading, for the standard URI, and for deterministic identifier issuance; only then does the word "join" mean anything. ④ A plausible-sounding sentence cannot be written at all — instead of grading a generative model's hallucinations after the fact, a statement without a grounding identifier is made unable to pass through the type system. And I have written down what all four cost: slow consensus, and early decisions that are expensive to undo.
Chapter 1. A Question of Order

What has to be decided before the data arrives

A meeting about building a knowledge graph usually opens with data. Which sources exist, how many records, in what format, and how we will load them. Yet the file that actually lands in the first commit is not data. It is a dictionary. What shall we call a class, what counts as a relation, what are that relation's domain and range, and which key decides that two records refer to the same thing. The data comes after.

The temptation to reverse this order is strong. The last dozen years of data engineering have leaned toward "load first, interpret later," and for logs and event streams that lean is mostly right — decide the schema at read time and a change upstream will not stop the pipeline. A knowledge graph is different, because a great many of the questions it is built to answer are questions of identity. Is this record and that record the same building? Is this road that road? Do two sources point at one institution or two? Identity is not the kind of judgement you can improvise at read time.

Naming things before you load them is not bureaucracy. It is the only way to make a join possible later.

Let me fix the vocabulary first. A knowledge graph is a data structure that puts entities in nodes and facts about them on edges. An ontology is the conceptual layer that governs which kinds of nodes and edges may exist in that graph. Technical discussions split these into the T-box (the concept level — classes, relations, constraints) and the A-box (the instance level — the actual instances). In standard vocabulary, RDF is the format for writing facts as subject–predicate–object triples, OWL is the language for describing what classes and relations mean, and SHACL is the language for validating that a data graph conforms to a declared shape. All three are W3C Recommendations. To fix the schema first is, in short, to settle the T-box before filling the A-box.

The address domain is unusually well suited to enforcing that order. First, a national standard already exists: the "Address Information Knowledge Graph Model" standard (Parts 1–3) defines the class system, the relation system and the URI rules in a document. Second, several organisations refer to the same entities from their own separate systems — different answers about the same building really do occur, and the problem is recognised as such. Third, the answers need evidence. When a public system says "the administrative district responsible for this address is here," that sentence has to be able to cite its source.

So on this project I decided to keep the order. The ontology sits above the code, and data may only enter in a shape the ontology has permitted. Below I set out, in four items, what that decision bought. I hope it does not read as a success story; the last chapter records what it cost.

Chapter 2. The First Return

Documents can no longer drift from the implementation

Plenty of organisations fix their schema in a document. Few have a document that matches the code. The reason is obvious: people edit the document and people separately edit the code, so given enough time the two must diverge. It starts as a trivial discrepancy, and at some point nobody believes the document any more. The benefit of having fixed the schema first evaporates with it.

The remedy chosen here was not to manage the document more diligently but to remove the path along which drift is possible. The single source of truth is neither prose nor code; it is a class dictionary in which the ontology is written down as data. Each entry in that dictionary carries its English label, its Korean alias, the axis the class belongs to, and its business key. And the web edition of the standard spec, the RDF/OWL ontology file, the JSON-LD context, the SHACL shapes, the data dictionary, and the database constraint and index statements are all generated from it.

The effect shows up immediately. Add one class and a row appears in the spec's table, a class declaration appears in the RDF, one node shape for that class appears in the SHACL, and a uniqueness constraint plus a business-key index appear in the database. There is no need to edit six places six times, and no chance of forgetting one of the six. Put the other way round: a class that is in the spec but missing from validation cannot exist.

Extension is isolation, not contamination. Take the standard as your source of truth and you hit a wall soon enough, because concepts the standard does not have will certainly turn out to be necessary. Entrances; the relation by which an administrative district administers a legal district; the relation by which a road passes through a legal district; the entity-resolution relation asserting that two different sources point at the same thing — without these the graph cannot answer real questions. But slip them quietly into the standard dictionary and the word "standard" stops meaning anything. So three beats became the rule: admit the need, prevent the contamination, feed it back as a proposal. Concepts outside the standard are registered separately in an extension dictionary, and from the registered entries a standard-revision proposal is generated automatically and returned to the standards side. If a tool does not enforce this, then on some night somebody will quietly add one more class.

There is a case where that feedback path actually worked. Object addresses were being handled through thirteen mappings at first, until it emerged that the source treats twenty-five kinds of thing quite differently from one another. Put bus stops, post boxes and tsunami emergency shelters in the same drawer and you cannot answer a query about "shelters nearby." So the standard was revised so that each of the twenty-five is handled as its own class. Classes grew from forty-two to fifty-four and relations from sixty-one to seventy-three. What matters is not that they grew but that the growth happened in one dictionary. Correcting a mapping means editing that one file; the code is untouched.

The same discipline applies to relations. The hierarchical relations the standard defines are registered as triples of name, domain and range, and the uniqueness key is that same triple — the fact that a relation with one name is registered separately for each domain/range combination simply follows the structure of the standard text. Spatial and semantic relations, which the standard does not define, are defined newly in a separate layer and tagged with a different category. Someone reading the graph has to be able to tell which edges carry the authority of the standard on their back and which are our own judgement.

Chapter 3. The Second Return

You get to choose what stays open and what gets locked

It would be unfortunate if "fix the schema first" were read as "nail everything down in advance." The important decision is not what you nail down but what you leave open, and being able to make that choice explicitly is the second return on schema-first.

In ontology terms the question splits into the open-world and closed-world assumptions. Under the closed-world assumption, what is absent from the data is false — this is how a relational database behaves. If a building has no entrance record, that building has no entrance. Under the open-world assumption, what is absent from the data is merely unknown; OWL reasoning rests on this assumption. From the fact that a building has no entrance record you cannot conclude that it has no entrance.

In the address and disaster domains this distinction is not a matter of academic taste, because missing source data is routine. Institution lists with no coordinates, buildings with no contact-point information, car parks with no object address assigned. Read those absences as "none" and the system will be confidently wrong. "There is no shelter nearby" means something entirely different when there truly is none than when the data simply has not been loaded — and yet the sentence is identical.

Open world versus closed world is not a theoretical question. It is the question of what the sentence "there is none" is allowed to mean.

So the tools were assigned separately. The meanings of classes and relations are described in open-world vocabulary (RDF/OWL), while the minimum shape the actual graph must satisfy is locked down by closed-world validation (SHACL). The SHACL shapes keep one node shape per class, require the deterministic identifier, the standard URI and the Korean alias as common mandatory properties, and layer that class's business key on top as required. The identifier is constrained down to a regular-expression pattern. At the database layer, every class carries an identifier uniqueness constraint and an index on the business key. In short: what an entity is is left open; the minimum conditions under which an entity may be called an entity are closed.

The open side was designed just as explicitly. The path by which external public data attaches to the graph is attempted in three tiers — joining on the address code is strongest, joining by coordinate comes next, and joining by area containment is weakest. Each tier is assigned a different confidence value, and if none of the three attaches, no link is created and only the record is preserved. That is a schema decision. It forbids "attach it anyway and fix it later," and it makes the existence of a link carry information in itself. A record that failed to attach remains a gap that can be filled later; a wrongly attached link quietly eats away the credibility of the whole graph.

The same thinking governs relation generation. Spatial and semantic relations are produced not by hardcoded procedures but by declarative rules. Which road a building fronts is judged from the actual contact point between entrance and road, falling back to the road that assigned the address only when contact data is missing, and lowering the confidence when it does. Area containment is cross-validated between spatial containment and the legal-district code. Because the rules are declarations rather than code, they can be registered, edited, disabled, recomputed and deleted from a web console, and every operation is recorded in an audit log. The advantage of this approach showed up more plainly in the paper that ran alongside: because the rules are declarative specifications independent of any region, the framework was portable to other cities providing equivalent open data.

Chapter 4. The Third Return

Identifiers exist before the model does

The third return on schema-first sounds the dullest and is in fact worth the most. Write the business key alongside each class in the dictionary and that one line becomes the basis for three things: the merge key for idempotent loading, the local identifier in the standard URI, and the sequence in deterministic identifier issuance. Because all three draw on the same source, all three cannot disagree.

Why does this matter? Without a business key, the phrase "the same entity" is undefined. Undefined, and loading twice produces two nodes; two nodes, and the edges hanging off them fork; and on a forked graph no query can be trusted. The problem also gets harder to find as the data grows. Working out after the fact which few of a million nodes are in fact the same building is orders of magnitude more expensive than fixing the key at the start.

The identifiers on this project are issued by rule rather than by hash — a domain code, a spatial cell, an above- or below-ground level, a generation, a deterministic sequence, and a check character, concatenated. A single building number ends up looking like BD-357CA3FE-G0-00-913547-I. Rules were chosen over hashes for three reasons. First, the same sources always give the same value, so re-running the load, or rebuilding from scratch on a different machine, yields the same identifier. Second, the spatial cell lives inside the identifier, so the value alone tells you roughly where the thing is. Third, the check character filters out, immediately, a key mangled somewhere in transit. And the identifier is assigned not only to nodes but to edges as well. With identifiers on edges you can trace "where did this fact come from" one fact at a time.

Why the standard URI and the internal key coexist. The standard requires a web URI for every node. Its form is, under the namespace, /id/{class}/{local id}, where the class label is converted to lower snake case (hub and abbreviation classes get an override mapping) and the local id is the business key joined with hyphens, zero-padded and lowercased. But a URI can change when the standard is revised — rename a class and the URI changes with it. So both are kept: an external identifier that may change and an internal key that may not. When regions are added one after another, an internal key already issued is inherited as it stands, only the collisions are reissued, and the endpoints of edges are remapped so that immutability holds. Identifier immutability is not preserved by declaring it. It is preserved by having the inheritance, collision and remapping procedures built beforehand.

There was one moment when this design repaid itself all at once. When the register of local-government invested and funded institutions was linked in, that source had no coordinates. The usual remedy is to attach an external geocoding service. But the graph already held building-number nodes densely, each with its business key, and the address codes in the institution list matched those keys. So 857 institutions were geocoded by the graph's own code join, with no external service at all. Once a graph is dense enough and its keys are consistent, the graph becomes the geocoder. A model cannot do this in its place. Give a language model an institution's name and ask for coordinates and plausible numbers come back, but there is nothing underneath them.

And when the keys are honest, the graph can audit its own sources in return. Cases where the spatial containment and the code disagreed were detected as quality signals, and cross-validating object addresses against national standard datasets produced car parks with no object address assigned as candidates for assignment, which went into the standard-revision proposal. Stop assuming the source is always right and the graph becomes a validator rather than a consumer.

How far this argument runs when there is more than one layer is a separate matter. Meshing two graphs built for different purposes over the same entities needs both a vocabulary crosswalk and a settled key, and that story is told in "Where, and What Happened." This piece is about the discipline inside one layer.

Chapter 5. The Fourth Return

A plausible-sounding sentence cannot be written at all

This is the part I most wanted to write. Anyone attaching a generative model to a knowledge graph will almost certainly meet the hallucination problem, and two prescriptions usually arrive first: writing "do not make things up" into the prompt, and grading the generated answer after the fact. Both are useful and both are probabilistic. A request may not be honoured, and a grader may miss.

Fix the schema first and a different kind of prescription becomes available: not reducing hallucination but removing the place where hallucination could be expressed. Four layers of refusal sit on the address agent in this project, and the four are different in kind.

First, writes blocked at the type level. The agent object refuses a writable backend outright, in its constructor. A wrong value does not raise an exception somewhere mid-run; it is rejected as a type error at the moment the object is created. What that one line does is delete from the program the very path by which a model-authored sentence could be recorded into the graph. Whatever the prompt asks, however confident the model is, there is no write, so there is no contamination.

Second, citations required. A fact object is not constructed without the identifier of the node that grounds it. If the citation is empty, or if the identifier and URI are missing from the citation, a citation error is raised. Here the schema intervenes decisively. Because the previous chapter locked the deterministic identifier and the standard URI in as mandatory properties of every node, "evidence that can be cited" exists everywhere in the graph. Had the schema not made them mandatory, mandatory citation could not be implemented. The two decisions are one body.

Third, post-generation cross-checking. The language model only does the work of stringing supplied facts into sentences. The resulting sentence is checked, down to digit boundaries, against whether its figures and names really do appear in the collected facts. Fail the check and the sentence is not adopted.

Fourth, deterministic fallback. The place left by a rejected sentence is not filled with silence but with a sentence assembled deterministically. A less fluent answer goes back, but one with evidence behind it.

Reducing hallucination and removing the place where hallucination could be expressed are different kinds of guarantee. The first is a probability; the second is a type.

What is interesting about this structure is that the character of the remaining errors changes. In earlier work in the same line we confirmed that when all reasoning is performed by graph traversal and the language model's role is restricted to generating sentences, the observed errors stem from gaps in knowledge rather than from fabrication. That is a more important change than a gain in accuracy. Fabrication is something a user cannot notice; a gap is something a user can. "That information is not in the graph" is an answer from which the user can decide what to do next, and a plausible wrong answer is not. Choosing a good failure mode comes before achieving good performance.

When validation audited the schema itself. The unexpected dividend of schema-first was that the validation layer catches errors in the schema itself. The business key of the national basic-district number class originally included the town/township/district code. Read the address hierarchy top-down and that is the natural design. But running SHACL validation against the real graph flagged the entire sample as violations. The cause was not the data but the concept: national basic districts are assigned at the municipal level, independently of town and township boundaries, so that class has no such code in its system at all. The business key was corrected. Had the validator been written by hand rather than generated from the dictionary, the hand-written validator would have shared the hand-written schema's misconception and the violations would never have surfaced. The value of generating validation from the schema was recovered once more, right there.

One thing should be said plainly. These four layers do not make the model trustworthy. They make it unable to contaminate the graph and unable to circulate ungrounded sentences. Judgement is still human. Where address and spatial information touches safety or public decisions, the outputs have to be subject to review by field experts, and adjustable values such as weights belong in configuration rather than nailed into the code. The role of software is not to make the decision but to put faster and more accurate material into the hands of the person who does.

Chapter 6. What It Cost

Why schema-first is expensive, and what is left

Having written down four things bought, fairness requires writing down the price. Schema-first is slow. You hold meetings instead of loading data. Days can go on the name of a single class. Take the standard as your source of truth and one more stage of slowness attaches: revising a standard requires human consensus, and consensus moves far more slowly than code. The extension dictionary and the revision-proposal feedback path exist precisely to survive that difference in speed.

And early decisions are expensive to undo. Change a class definition after you have begun issuing identifiers and the question becomes what to do about keys already out in the world. The inheritance, collision reissuance and edge-endpoint remapping procedures described earlier are machinery for managing that cost, not for eliminating it. Schema-first means less "get it right at the start and life is easy" and more "what to do when you got it wrong is already decided."

So I cannot claim the approach is always right. In domains where several organisations refer to the same entities from their own systems, where answers require public evidence, and where the system outlives the project, fixing the schema first is almost always cheaper. Conversely, for exploratory analysis, for an early product whose hypotheses change weekly, or for a pipeline whose upstream schema wobbles outside your control, load-first-interpret-later is better. The criterion is not the size of the data but whether identity matters.

Let me also record the homework. First, the decision to use open-world vocabulary alongside closed-world validation was pragmatic but left a duality. RDF/OWL is generated as a standard artefact, while operational queries run over a property graph. The two representations come from the same dictionary and so cannot diverge, but no OWL reasoner sits in the operational path. Which inferences belong at validation time and which at query time is not yet sorted out.

Second, there is no time axis in the schema. To hold address data whose source updates quarterly and sensor signals that flow by the second in the same graph, you have to decide where to record when a fact was true. Incremental updates are handled with manifests, watermarks and tombstones, with recomputation confined to the changed records and their spatial neighbours — but that is a design for updating, not a design for time. This one has no answer yet.

Third, deciding an ontology is in the end a human judgement. What counts as a class, and how much counts as one entity, is not settled by the data. Even the decision to split the twenty-five kinds of object address into separate classes came out of a purpose: that only by splitting them could you ask about shelters. A schema is not a fact about the world but the shadow of the question you intend to ask. Which means that fixing the schema first also means deciding, before you load the data, what you are going to ask of it.

In closing — the dull decision that makes room to move. The sentence I heard most often during this work was "can't we decide that later?" The answer was usually no, and the reason was neither discipline nor perfectionism. Decide later and by then two systems are already calling the same building by different names, identifiers have already gone out into the world, and a hand-written validator is already sharing a hand-written misconception. Fix one dictionary first, on the other hand, and adding a class, adding a region, or attaching a language model each becomes a day's work. What the dullness of schema-first buys is not only correctness. It is the freedom to move quickly later.
