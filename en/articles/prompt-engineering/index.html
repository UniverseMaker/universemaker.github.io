The Science of Prompt Engineering: Design Principles That Raise Language-Model Performance

Even the same model answers differently depending on how you ask. How to treat prompting as 'engineering' rather than a 'knack.'

DP
Daeseung Park AI & Software Systems Engineer · KAIST June 2026 · 14 min read
1-min summary The performance of a large language model (LLM) is not decided by model size alone. Even with the same model, how you compose the input — that is, prompt design — can swing accuracy by tens of percentage points. This piece proposes treating a prompt not as a lucky ‘incantation’ but as a reproducible ‘experiment.’ Assigning a role, step-by-step reasoning (Chain-of-Thought), worked examples (few-shot), locking down the output format, and a systematic evaluation loop — we walk through five levers that raise results without changing the model.
Chapter 1. The Problem

Why the Same Model Is Brilliant Some Days and Dim on Others

Anyone new to language models runs into the same bewilderment first. The model that wrote flawless code yesterday returns nonsense to the same request today. The model has not changed. What changed is the sentence we handed it. A single space, the order of the examples, the presence or absence of one line — “think step by step” — these seemingly trivial differences decide the outcome.

This is not a bug; it is the very nature of a language model. An LLM is not a database that ‘looks up’ facts but a probabilistic machine that ‘predicts’ the most plausible token to follow a given context. The context we supply — the prompt — is therefore the initial condition that sets the model’s path of thought. Change the initial condition and the trajectory changes with it. Prompt engineering is the work of designing that initial condition so the intended result emerges.

A prompt is not an incantation cast on the model; it is the initial condition that sets the model’s path of thought.

I have published a study quantifying how prompt design for generative AI affects performance in the Journal of Web Engineering (SCIE). The most important lesson from that work turned out to be surprisingly simple. A prompt is not a matter of intuition but a thing to be measured. What can be measured can be improved, and what can be improved becomes engineering.

Chapter 2. Five Levers

How to Change the Result Without Changing the Model

Switching to a bigger model is the most expensive fix and sometimes the laziest. Before you reach for it, there are five design levers worth checking. Each helps on its own, but together they work by multiplication.

1. Fix the role and context first

“Review this code” and “You are a security-focused code reviewer with fifteen years of experience; flag the vulnerabilities in the code below in order of severity” produce entirely different answers. When you assign a role, the model narrows its output to the distribution of contexts in which that role is active. A vague question invites a vague average; a specific role invites specific expertise.

2. Force the reasoning to unfold (Chain-of-Thought)

On hard reasoning problems, telling the model to “just give the answer” makes it wrong often. Ask it instead to “lay out the reasoning step by step, then draw a conclusion,” and accuracy climbs noticeably. The reason is that when the model ‘unfolds’ its intermediate reasoning into output tokens, those tokens in turn become the context for the next step and sustain a longer chain of thought. Make the thinking visible, and the thinking grows more accurate.

Practical tip. You often want to hide the reasoning from the end user. In that case, still have the model reason step by step, but instruct it to “print the conclusion only on the last line, in the form Final answer:,” and then extract just that line in post-processing. You get accuracy and a clean output at once.

3. Show with examples instead of explaining in words (Few-shot)

The trickier the desired output format or tone, the more overwhelmingly effective it is to show two or three good examples rather than spell out the rules at length. A model follows the pattern of concrete cases better than an abstract description of a rule. The examples must be ‘representative,’ though. Feed it an exceptional or ambiguous example and the model mistakes the exception for the rule.

4. Turn the output format into a contract

The moment you integrate a prompt into a system, a human-readable answer becomes secondary and a ‘machine-parseable answer’ becomes the point. A JSON schema, a fixed header, an agreed delimiter — nailing the output format down as an explicit contract sharply cuts the chance that downstream code breaks. When you enforce a format, it helps to add a negative instruction alongside it: “output only the format below and attach no other explanation.”

5. Do not try to get it right in one shot

A good prompt is never finished in one pass. The proper method is to build a small evaluation set (20–50 representative inputs) and run a loop that tweaks the prompt bit by bit while measuring accuracy and format-compliance. With that loop, the impression “this looks better” turns into the fact “this is eight percentage points higher.”

Chapter 3. Measurement

What It Means to Treat a Prompt as an Experiment

This is where the ‘engineering’ truly begins. The moment we judge which of two prompts is better by impression, we step into the realm of superstition. The procedure I adopted in my research is simple but strict.

StepWhat you doOutput
1. Define the taskState the definition of success in one sentenceEvaluation criteria
2. Build the evaluation setRepresentative inputs + answers / scoring rulesA fixed test set
3. Draft candidates2–5 prompt variantsA comparison group
4. MeasureScore them against the same setQuantitative scores
5. IterateAdopt the winner, analyze the failuresThe next hypothesis

The real value of this procedure lies not in the scores themselves but in the fact that it forces you to look at the failures. Gather where and how the model goes wrong, and the direction for the next prompt rises naturally out of the data. Instead of a vague “make it better,” you get a concrete diagnosis: “it breaks the format on this type of input.”

Chapter 4. Pitfalls

Three Common Misconceptions

First, the illusion that longer is better. A model does not grow smarter as the prompt grows longer. If anything, the key instruction gets buried in the noise and ignored. A good prompt is not long but ‘dense.’ Every sentence should bear on the output.

Second, the illusion that once it works, you are done. When the model version goes up, the same prompt can behave differently. Version-control your prompts as you would code, and run a regression test with your evaluation set every time the model updates.

Third, the illusion that the model ‘understands.’ A model does not grasp meaning; it stitches patterns together. “Just handle it well on your own” is therefore the most dangerous instruction of all. Whatever we leave unspecified, the model fills in with the average. And the average is exactly what mediocrity is.

Closing

From Incantation to Design

Prompt engineering is not a matter of reciting magic spells. It is a thoroughly engineering activity: understanding how the model works, deliberately designing the initial condition that is the input, and measuring and improving the result. Models will only grow more powerful. Yet the ability to design ‘what to ask, and how’ remains the human’s share, no matter how far the model advances. The old truth that good questions make good answers only grows sharper in the age of AI.
